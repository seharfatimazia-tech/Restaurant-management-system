DBMS Foundations

Primary Keys & Foreign Keys in Action

Primary Key (PK)

Uniquely identifies each record. Always unique and non-null (e.g. customer.id, orders.id).

Foreign Key (FK)

References a PK in another table to enforce Referential Integrity (e.g. address.customer_id → customer.id).

[CUSTOMER] PK: id = 101 (Emily Watson) │ └───< [ADDRESS] PK: id = 501, FK: customer_id = 101, FK: delivery_zone_id = 2 │ └───< [DELIVERY] PK: id = 701, FK: address_id = 501, FK: rider_id = 6
Foreign key constraints prevent orphaned records and enforce real-world business links.
Database Normalization

Meeting 3NF & BCNF Standards

1NF (Atomicity)

Every field holds an atomic single value. Ordered items are separated into child rows in order_item.

2NF (No Partial Dep.)

In composite associative tables like recipe(menu_item_id, ingredient_id), required quantity depends on both keys.

3NF (No Transitive Dep.)

Auth credentials (user_account) are isolated from employee profiles (staff). Historical order prices are immutable.

BCNF (Superkeys)

Every non-trivial functional dependency X → Y has X as a superkey with explicit database UNIQUE constraints.

Prevents insertion, deletion, and update anomalies across all 21 models.

Operational Workflow 3

Atomic Inventory Depletion via Recipes

Core DBMS Rule: When an order is completed, raw ingredients must be deducted according to the Bill of Materials (BOM) in a single atomic transaction.

Order #ORD-1001 Completed (2x Margherita Pizza) │ ├── Dish Recipe: Pizza Dough (0.25 kg), Mozzarella (0.20 kg), Sauce (0.15 L) │ └── [ATOMIC COMMIT BLOCK] 1. Deduct: 0.50 kg Pizza Dough from ingredient.current_stock 2. Deduct: 0.40 kg Mozzarella from ingredient.current_stock 3. Deduct: 0.30 L Tomato Sauce from ingredient.current_stock 4. Write 3 negative signed entries to stock_transaction ledger 5. Release dining table to 'Available' 6. Record event in audit_log
If any deduction step fails, the entire transaction rolls back cleanly.

Operational Workflow 5

Billing, Payments & Constraints

Core DBMS Rule: Payment amount cannot exceed current bill balance.

Bill #BILL-1002 ──> Total: $51.84 | Paid: $0.00 | Remaining Balance: $51.84 Scenario A: Cashier enters $60.00 Payment └── Check: $60.00 > $51.84 └── RESULT: [HTTP 400 Bad Request] Rejected by backend constraint check! Scenario B: Cashier enters $51.84 Payment (or Partial $30.00) └── Check: Valid ≤ Remaining Balance └── RESULT: [HTTP 201 Created] Payment row written; balance becomes $0.00 (Status: 'Paid')
Eliminates negative ledger balances and accounting discrepancies.
